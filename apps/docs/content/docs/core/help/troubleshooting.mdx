## `useApi must be used within an ApiProvider`

`useApi()` was called from a component with no `ApiProvider` above it.

It throws rather than returning `undefined`, because a silent `undefined` would
fail later at the call site with nothing pointing back to the real cause.

Wrap the tree — see [ApiProvider](/docs/react/api-reference/provider). In Next.js
App Router, remember the provider is a client component and only covers the
subtree it wraps.

## CORS errors

```
Access to fetch at 'https://api.example.com' has been blocked by CORS policy
```

This is the browser refusing the response, not api-zero failing. **No client-side
setting can turn it off** — it is enforced by the browser on behalf of the
server.

Fix it on the server (`Access-Control-Allow-Origin`), or proxy the API through
your own origin in development.

If the API needs cookies across origins, `credentials: "include"` is required on
your side *and* `Access-Control-Allow-Credentials` on theirs. Note that with
credentials, the server may not answer `Access-Control-Allow-Origin: *` — it must
name your origin exactly.

```typescript
const api = createClient({
  baseURL: "https://api.example.com",
  credentials: "include",
});
```

Check `error.isTimeout` to tell a timeout apart from `error.isAborted`, which

the second, not the first — and it is not a bug.

## `error.isNetworkError === true`

The request never reached a response: DNS, connectivity, a refused connection, or
CORS preflight rejection. The status is `0` because there is nothing to report.

Log the resolved URL from an interceptor before assuming the server is down —
a wrong `baseURL` produces exactly this.

## A request is not being retried

Most often, because **retries are off by default**. Configure them first.

With retries on, a request is still skipped when:

- The method is not idempotent. `POST` and `PATCH` never retry automatically —
  set `retryUnsafeMethods: true` only if the endpoint is genuinely safe to
  repeat.
- The error is not retryable. A `400` or `404` will fail identically next time.
- The request was cancelled. Aborts are never retried.

See [Retries](/docs/core/guides/retries).

## Progress callbacks never fire

`fetch` cannot report upload progress, so api-zero switches to `XhrTransport`
when `onUploadProgress` or `onDownloadProgress` is present.

XHR exists only in browsers. In Node or on an Edge runtime there is nothing to
switch to, so keep progress callbacks on the client side.

Check `event.lengthComputable` before dividing: without a `Content-Length` the
total is unknown and the percentage is meaningless.

## Query parameters arrive wrong

Two usual causes:

- **Arrays.** There is no standard encoding. Match your backend with
  `paramsSerializer.arrayFormat`.
- **Objects and dates.** They are stringified, so a nested object becomes the
  literal `[object Object]`. Flatten them and format dates yourself.

See [Query parameters](/docs/core/guides/requests).

## `Content-Type` is missing on a `FormData` upload

That is deliberate. A multipart body needs a boundary parameter that only the
platform can generate, so the header is removed and the browser sets it. Setting
it yourself produces a request the server cannot parse.
