Everything that can go wrong arrives as an `ApiError`: HTTP status codes,
network failures, timeouts, caller cancellation and validation failures alike.

That uniformity is the point. Native `fetch` rejects with
`TypeError: Failed to fetch` for a DNS failure and *resolves* successfully for a
500, so a correct handler needs two unrelated code paths. Here there is one.

## Catching it

<include meta='title="users.ts"'>../../../../../../examples/src/error-handling.ts</include>

Check `instanceof ApiError` before touching its properties. A bug inside your own
`then` handler is still a plain `Error`, and swallowing it as if it were a
transport failure hides real defects.

## Properties

| Property | Type | Meaning |
| -------- | ---- | ------- |
| `status` | `number` | HTTP status, or `0` when no response arrived. |
| `statusText` | `string` | HTTP status text. |
| `data` | `TData \| undefined` | Parsed error body, when the server sent one. |
| `request` | `RequestContext \| undefined` | Method, resolved URL, headers, params, attempt. |
| `response` | `Response \| undefined` | The native response, when there was one. |
| `cause` | `Error \| undefined` | The original error, preserved. |
| `attempt` | `number` | Which attempt produced this failure. `1` when retries are off. |
| `isTimeout` | `boolean` | The request exceeded its timeout. |
| `isNetworkError` | `boolean` | The request never reached a response. |
| `isAborted` | `boolean` | Cancelled through the caller's `AbortSignal`. |
| `isValidationError` | `boolean` | The response arrived but failed validation. |

<include meta='title="users.ts"'>../../../../../../examples/src/error-context.ts</include>

<Callout type="info">
  `isTimeout` and `isAborted` stay distinct. A server that was too slow and a
  request your own code cancelled call for different handling — one is worth
  reporting, the other is routine. Most clients collapse both into a generic
  abort and lose that.
</Callout>

## Helpers

| Method | True when |
| ------ | --------- |
| `is4xx()` | `status` is 400–499. |
| `is5xx()` | `status` is 500–599. |
| `isUnauthorized()` | `status` is 401. |
| `isForbidden()` | `status` is 403. |
| `isNotFound()` | `status` is 404. |
| `isValidation()` | The response failed validation. |
| `isRetryable()` | The failure is worth trying again — see below. |

### `isRetryable()`

Encodes the same policy the retry engine uses, so you can reuse it in your own
logic:

- **Never** for a caller cancellation or a validation failure. The first was
  intentional, the second will fail identically next time.
- **Always** for network failures and timeouts.
- **Yes** for `408` and `429`, and for any `5xx`.
- **No** for every other `4xx`: a `400` or a `404` is about your request, and
  repeating it wastes time to receive the same answer.

## Serializing

`toJSON()` returns a flat, log-friendly object with the message, status,
flags, attempt, and the resolved `url` and `method` — without the native
`Response`, which does not serialize.

```typescript
logger.error("request failed", error.toJSON());
```

## Constructing one

`ApiError.from(message, options)` builds one with an options bag instead of the
positional constructor. Useful in a custom transport or a test double.

```typescript
throw ApiError.from("Upstream unavailable", {
  status: 503,
  isNetworkError: true,
});
```
