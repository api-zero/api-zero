**Retries are off by default.** A client that silently repeats requests is a
client that can charge a customer twice. Turning them on is a decision you make
per API.

## `RetryConfig`

| Option | Type | Default | Description |
| ------ | ---- | ------- | ----------- |
| `attempts` | `number` | — | Total attempts, including the first. `1` or less disables retrying. |
| `delay` | `number` | — | Base delay in milliseconds. |
| `maxDelay` | `number` | `30000` | Upper bound for any single wait. |
| `backoff` | `"exponential" \| "linear" \| fn` | `"exponential"` | How the delay grows. |
| `jitter` | `boolean` | `true` | Randomize the delay. |
| `respectRetryAfter` | `boolean` | `true` | Obey a `Retry-After` header. |
| `retryMethods` | `HttpMethod[]` | `["GET", "PUT", "DELETE"]` | Methods eligible for automatic retry. |
| `retryUnsafeMethods` | `boolean` | `false` | Also allow `POST` and `PATCH`. |
| `retryCondition` | `(error, attempt) => boolean` | — | Replaces the default eligibility test. |
| `onRetry` | `(event: RetryEvent) => void` | — | Called before each wait. |

## What retries, and what does not

A failure has to clear three gates before a retry happens.

**1. Cancellation always wins.** An aborted request is never retried. You asked
for it to stop.

**2. The method must be eligible.** `GET`, `PUT` and `DELETE` are idempotent:
doing them twice has the same effect as doing them once. `POST` and `PATCH` are
not, so they never retry automatically.

**3. The error must be worth retrying.** By default that means what
[`isRetryable()`](/docs/core/api-reference/error) reports: network failures,
timeouts, `408`, `429` and any `5xx`. Not a `400`, not a `404`, not a validation
failure — those will fail identically next time.

<Callout type="warn">
  **Supplying `retryCondition` bypasses the method check.** It replaces the whole
  eligibility test, so a condition like `(error) => error.is5xx()` will retry a
  `POST` even with `retryUnsafeMethods: false`. If you write one, decide about
  method safety inside it — `error.request?.method` is right there.
</Callout>

## How long it waits

Computed fresh for every attempt, in this order:

1. **`Retry-After` first.** If the response carries one and
   `respectRetryAfter` is not `false`, that value wins outright and backoff is
   skipped. Both forms are parsed: seconds (`Retry-After: 30`) and an HTTP date.
   The server knows when it will be ready; guessing over it is worse.
2. **Otherwise, backoff.** `exponential` gives `delay × 2^(attempt-1)` — 1s, 2s,
   4s, 8s. `linear` gives `delay × attempt` — 1s, 2s, 3s. A function receives
   `(attempt, error)` and returns milliseconds.
3. **Capped at `maxDelay`.**
4. **Jitter, if enabled.** Equal jitter: the delay is multiplied by a random
   factor between 0.5 and 1.

That last step is not decoration. When an outage ends, every client that was
retrying wakes up on the same schedule and hits the recovering server
simultaneously — a thundering herd that can knock it straight back down. Jitter
spreads them out. It only ever shortens a wait, never lengthens it past the cap.

## Observing retries

`onRetry` fires before each wait with a `RetryEvent`:

| Field | Meaning |
| ----- | ------- |
| `attempt` | The attempt that just failed. |
| `maxAttempts` | The configured total. |
| `error` | The `ApiError` that triggered the retry. |
| `delay` | Milliseconds about to be waited, jitter included. |
| `request` | The `RequestContext`. |

Retries that nobody can see turn a slow API into a mysteriously slow app. Log
this.

## Cancelling during a retry

Aborting while the client is waiting between attempts stops it immediately. The
sleep is signal-aware, so it does not run the delay out before noticing.
