---
title: Interceptors
description: Enrich every request, inspect every response, and recover from failures.
---

Interceptors are the extension point of the request lifecycle. Request handlers
run before the transport; response handlers run after the body is parsed.

```typescript
client.interceptors.request  // InterceptorManager<RequestContext, unknown>
client.interceptors.response // InterceptorManager<ResponseContext, ApiError>
```

`use(fulfilled?, rejected?)` returns a numeric id. `eject(id)` removes one,
`clear()` removes all.

## Request interceptors

A request handler receives the full `RequestContext` and returns it.

<include>../../../../../../examples/src/interceptor-request.ts</include>

The context is the resolved request, not the options you passed:

| Field | Meaning |
| ----- | ------- |
| `method` | The HTTP method. |
| `endpoint` | The path as the caller wrote it, e.g. `/users`. |
| `baseURL` | The base in effect for this request. |
| `url` | **The fully resolved URL**, base and query string included. |
| `body` | The body after request transforms. |
| `params` | Query parameters, before serialization. |
| `headers` | Normalized headers. Mutate these to add one. |
| `attempt` | `1` on the first try, higher on a retry. |
| `metadata` | Your own bucket. Nothing in the library reads it. |

<Callout type="warn">
  `url` is already complete. Building `${context.baseURL}${context.url}` for a
  log line produces the base URL twice — a mistake that survives review because
  the request still works and only the logs are wrong.
</Callout>

## Response interceptors

<include>../../../../../../examples/src/interceptor-response.ts</include>

The success handler receives a `ResponseContext`: the `request` that produced it,
the parsed `data`, `status`, `statusText`, `headers` and `timing`. Not a raw
`Response` — the body has already been read, transformed and validated.

The rejection handler receives an `ApiError`, and **it receives every failure
class**: HTTP status, network failure, timeout, cancellation and validation
alike. Errors are normalized before the chain runs, which is what makes the next
pattern possible at all.

## Recovering: refreshing an expired token

The canonical use for a rejection handler is turning a failure into a success by
fixing the cause and replaying the request.

<include>../../../../../../examples/src/auth-refresh.ts</include>

Three details are what separate this from a version that breaks in production:

1. **One refresh at a time.** Ten concurrent requests hitting a 401 must not
   trigger ten refreshes. The shared promise makes the rest wait for the first.
2. **The refresh call is excluded.** If refreshing itself returns 401, a handler
   that retries everything calls itself forever.
3. **The replay is tagged through `metadata`.** Without a marker, a replay that
   fails again re-enters the handler, and you are back to an infinite loop.

`metadata` exists for exactly this: request-scoped state that travels with the
context and that no header has to carry.

## Order and removal

Handlers run in registration order. `use()` returns an id:

```typescript
const id = client.interceptors.request.use(handler);
client.interceptors.request.eject(id);
client.interceptors.request.clear(); // removes all
```

Returning nothing from a request handler leaves the context unchanged, so a
logging handler does not have to return it — but returning it is clearer, and
required when you replaced it.
