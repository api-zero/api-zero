## Three packages, split by dependency direction

The split is not about size. It is about what each package forces you to
install.

`core` depends on nothing, so it runs anywhere with `fetch`. `react` and `zod`
peer-depend on their host library rather than bundling it — that matters more
than it sounds: `ZodValidationError` extends `ApiError`, and code everywhere
branches on `instanceof ApiError`. Two copies of core in one dependency tree
would make those checks silently return `false`.

## The request lifecycle

Every request follows the same path, and the order is part of the contract.

<Mermaid
  chart={`
sequenceDiagram
    participant Caller
    participant Transforms as Request transforms
    participant ReqInt as Request interceptors
    participant Transport
    participant ResTransforms as Response transforms
    participant Validation
    participant ResInt as Response interceptors

    Caller->>Transforms: body, params, headers
    Transforms->>ReqInt: transformed body
    ReqInt->>Transport: final RequestContext
    Transport->>ResTransforms: parsed response
    ResTransforms->>Validation: transformed data
    Validation->>ResInt: validated data
    ResInt->>Caller: result, or a normalized ApiError
`}
/>

1. **Request transforms** — client-level first, then per-request.
2. **Request interceptors** — receive the full `RequestContext`: method, resolved
   URL, body, params, headers, attempt number and a metadata bucket.
3. **Transport, wrapped in the retry policy** — `FetchTransport` everywhere,
   `XhrTransport` in browsers when upload or download progress is requested.
4. **Response transforms** — client-level first, then per-request. This is where
   `zodResponse` plugs in.
5. **Validation** — `validateResponse`, or a Zod schema.
6. **Response interceptors** — success handlers get a `ResponseContext` with
   parsed `data`, status, headers and timing. Rejection handlers get an
   `ApiError`.

The last point is the one that is easy to get wrong. **Errors are normalized
before the interceptor chain runs**, so a rejection handler sees HTTP failures,
network failures, timeouts and validation failures alike. A handler that
refreshes an expired token works because the 401 actually reaches it.

### Transport is a boundary, not an implementation detail

`Transport` is a public interface with a single method. Swapping it replaces the
entire network layer.

## The retry policy

Most clients either retry everything or retry nothing. Both are wrong.

- **By error** — retries network failures, timeouts, `408`, `429` and `5xx`.
  Never retries a caller cancellation, a validation failure or a `4xx` you
  caused: repeating those just wastes time and produces the same answer.
- **By method** — `GET`, `PUT` and `DELETE` are idempotent, so they retry by
  default. `POST` and `PATCH` do not, because a retried `POST` can create the
  same resource twice. Opt in with `retryUnsafeMethods` when you know the
  endpoint is safe.
- **Backoff with jitter** — exponential by default, capped by `maxDelay`, with
  randomness so a thousand clients recovering from the same outage do not
  stampede the server in lockstep.
- **`Retry-After`** — honored on `429` and `503`. When the server tells you when
  to come back, guessing is worse.
- **Cancellation during backoff** — aborting a request while it waits between
  attempts stops it immediately instead of sleeping out the delay.
