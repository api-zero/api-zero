every CI run. If an example stops matching the API, the build fails before the
page can mislead you.

## Create a client

Export this from a shared module. One instance carries your base URL, headers,
auth and retry policy for the whole application.

## Make a request

<include meta='title="users.ts"'>../../../../../../examples/src/http-verbs.ts</include>

The type parameter describes the response body. It is a static promise, not a
runtime check — for payloads you do not control, add
[`@api-zero/zod`](/docs/zod) and have it verified for real.

## Handle failure

<include meta='title="users.ts"'>../../../../../../examples/src/error-handling.ts</include>

Everything that can go wrong arrives as an `ApiError`: HTTP status, network
failure, timeout, caller cancellation and invalid JSON alike.

</Steps>

## Query parameters

<include meta='title="users.ts"'>../../../../../../examples/src/query-params.ts</include>

Arrays can be serialized as `brackets`, `repeat` or `comma` through
`paramsSerializer`, per client or per request.

<include meta='title="lib/api.ts"'>../../../../../../examples/src/auth-headers.ts</include>

## What an error carries

An `ApiError` is not just a message. It keeps the context you need to decide
what to do next.

<include meta='title="users.ts"'>../../../../../../examples/src/error-context.ts</include>

`isTimeout` and `isAborted` stay distinct on purpose: a request the server was
too slow to answer and a request your own code cancelled deserve different
handling, and most clients collapse them into one.

## Cancellation

<include meta='title="search.ts"'>../../../../../../examples/src/cancellation.ts</include>

Timeouts compose with caller cancellation into a single signal, and the
resulting error tells you which one fired.
