## Bearer tokens

Set the token once on the client. Every later request carries it.

<include meta='title="lib/auth.ts"'>../../../../../../examples/src/auth-bearer.ts</include>

This is the simplest correct approach and it is usually the right one. Reach for
an interceptor only when the token is not known when the client is created, or
changes between requests.

<Callout type="warn">
  On the server, a module-level client is shared by every request the process
  handles. Calling `setAuthToken` on it leaks one user's credentials into another
  user's request. In SSR, create a client per request, or pass the header per
  call.
</Callout>

## Reading the token per request

<include meta='title="lib/api.ts"'>../../../../../../examples/src/interceptor-request.ts</include>

Mutate `context.headers` and return the context. A request interceptor runs
before every attempt, so a token read here is always current — including on a
retry.

## Basic auth

`setBasicAuth(user, pass)` base64-encodes the pair into the `Authorization`
header. It is transport-level auth with no expiry, so there is nothing to
refresh.

## Refreshing an expired token

The interesting case: turning a `401` into a success by fixing the cause and
replaying the request.

<include meta='title="lib/auth-refresh.ts"'>../../../../../../examples/src/auth-refresh.ts</include>

Three details separate this from a version that breaks in production:

1. **One refresh at a time.** Ten concurrent requests that all hit a `401` must
   not trigger ten refreshes. The shared promise makes the rest wait for the
   first, which is also what stops a refresh endpoint from rate-limiting you.
2. **The refresh call is excluded.** If refreshing itself answers `401`, a
   handler that retries everything calls itself until the stack gives up.
3. **The replay is tagged.** `metadata` travels with the request context, so the
   retried request is recognisable and cannot re-enter the handler. Without a
   marker, a replay that fails again loops forever.

<Callout type="info">
  Retries and this are different mechanisms. The retry policy repeats a request
  unchanged, so it deliberately never retries a `401` — repeating a request with
  the same expired token produces the same `401`. Refreshing changes the request
  first, which is why it belongs in an interceptor.
</Callout>

## Signing out

`clearAuth()` removes the header. Anything already in flight keeps the old
token: it was attached when the request was built.
