`ApiProvider` publishes an `ApiClient` to React context. Every component below
it shares the same base URL, headers, auth, interceptors and retry policy —
which is the whole reason this package exists.

## Choosing how to provide it

### Pass an instance

<include meta='title="app/providers.tsx"'>../../../../../../examples/src/react-provider.tsx</include>

Creating it at module scope makes its lifetime explicit and its identity stable.
Nothing about a re-render can replace it, and a token set in one component is
visible to every other.

**This is the form to reach for by default.**

### Pass a config

<include meta='title="app/providers.tsx"'>../../../../../../examples/src/react-provider-config.tsx</include>

Convenient, and it carries a trap. An object literal in JSX is a **new object on
every render**. A naive provider would build a new client each time, discarding
any token set on the previous one — a bug that surfaces as "the user is randomly
logged out" and is miserable to track down.

`ApiProvider` guards against it by comparing the config's *contents* rather than
its identity: `baseURL`, `timeout`, `credentials`, `transport` and each header.

<Callout type="warn">
  That comparison is shallow. It cannot see through a changed `retry` object or
  a changed transform function, so a config varying in those will keep returning
  the same client. When your configuration is dynamic, build the client yourself
  and pass `client`.
</Callout>

### If you pass both

`client` wins and `config` is ignored. That is deliberate: an explicit instance
is a stronger statement of intent than a description of one.

## Reaching it

<include meta='title="components/sign-in-button.tsx"'>../../../../../../examples/src/react-use-api.tsx</include>

`useApi()` throws outside a provider rather than returning `undefined`, because
a silent `undefined` fails later at the call site with nothing pointing back to
the real cause.

<Callout type="info">
  In the Next.js App Router, `ApiProvider` is a client component. It only covers
  the subtree it wraps, and a server component cannot call `useApi()` at all —
  see [server rendering](/docs/react/guides/server-rendering).
</Callout>

## More than one API

### Nesting providers

<include meta='title="app/app.tsx"'>../../../../../../examples/src/react-provider-nested.tsx</include>

An inner provider shadows the outer one for its subtree. Each client keeps its
own headers and interceptors, so an auth token on one never travels to the
other — which is exactly what you want when the second service is a third party.

### When not to nest

If both APIs are yours and share credentials, one client with a per-request
`baseURL` override is simpler:

```tsx title="hooks/use-invoice.ts"
api.get<Invoice>("/invoices/1", { baseURL: "https://billing.example.com" });
```

Nesting earns its cost when the clients genuinely differ — different auth,
different retry policy, different interceptors.
