SWR fills the same role as TanStack Query: cache, revalidation and server-state
lifecycle. api-zero sits underneath it exactly the same way.

<include meta='title="hooks/use-user.ts"'>../../../../../../examples/src/react-swr.ts</include>

SWR passes the key to the fetcher, so when the key is the endpoint, api-zero
*is* the fetcher.

### Cancellation

<Callout type="warn">
  SWR does not hand an `AbortSignal` to the fetcher the way TanStack Query
  does. A superseded request keeps running until it completes — SWR simply
  ignores the result.
</Callout>

For a search box, or anything that fires per keystroke, that means one live
request per character. Hold the controller yourself:

<include meta='title="hooks/use-search.ts"'>../../../../../../examples/src/react-swr-cancellation.ts</include>

If cancellation matters to you, [TanStack Query](/docs/react/guides/tanstack-query)
gives you the signal for free.

### A global fetcher

Setting the fetcher on `SWRConfig` removes the per-call boilerplate, at the cost
of the client being captured once rather than read from context.

```tsx
<SWRConfig value={{ fetcher: (url: string) => api.get(url) }}>
  <App />
</SWRConfig>
```

That is fine when the client is module-scoped, and wrong on a server, where the
client must be per request.
