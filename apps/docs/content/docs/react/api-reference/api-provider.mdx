`ApiProvider` puts one `ApiClient` in React context so every component below it
shares the same base URL, headers, auth, interceptors and retry policy.

## Props

| Prop | Type | Description |
| ---- | ---- | ----------- |
| `client` | `ApiClient` | An instance you created yourself. Preferred. |
| `config` | `ApiClientConfig` | Configuration to build a client from, when you have no instance. |
| `children` | `ReactNode` | The subtree that gains access to the client. |

Pass `client` or `config`. If both are present, `client` wins.

## Recommended: pass an instance

<include meta='title="app/providers.tsx"'>../../../../../../examples/src/react-provider.tsx</include>

Creating the client outside the component tree makes its lifetime explicit and
its identity stable. Nothing about a re-render can replace it.

## Passing `config` instead

```tsx
<ApiProvider config={{ baseURL: "https://api.example.com", timeout: 10_000 }}>
  <App />
</ApiProvider>
```

This is convenient, and it carries a trap worth understanding. An object literal
in JSX is a **new object on every render**. A naive provider would build a new
client each time, discarding any token set on the previous one.

`ApiProvider` guards against that by comparing the config's contents — `baseURL`,
`timeout`, `credentials`, `transport` and each header — rather than its identity.
A literal with unchanged values keeps the same client.

That comparison is shallow, so it cannot see through a changed `retry` object or
a changed transform function. When your configuration is dynamic, build the
client yourself and pass `client`.

## Nesting

Providers nest. An inner one shadows the outer for its subtree, which is how you
talk to a second API without giving up the first.

```tsx
<ApiProvider client={mainApi}>
  <Dashboard />
  <ApiProvider client={billingApi}>
    <Invoices />
  </ApiProvider>
</ApiProvider>
```
