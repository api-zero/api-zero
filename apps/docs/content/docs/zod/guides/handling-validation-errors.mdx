`ZodValidationError` extends `ApiError`, so it flows through the same catch
blocks, the same interceptors and the same `instanceof ApiError` checks as every
other failure. Code that already handles errors does not need a new branch to
avoid crashing on this one.

## Which side failed

`target` says `"response"` or `"body"`, and they call for opposite responses.

<Accordions>
  <Accordion title='target: "body" — your bug'>
    The request was malformed before it was sent. Nothing reached the server.
    Surface the issues to whoever built the payload: a form, a caller, a script.
    This is recoverable in the UI.
  </Accordion>
  <Accordion title='target: "response" — their change, or your schema'>
    The server sent something the contract does not describe. Either the API
    changed or the schema is wrong. This is not recoverable in the UI — report
    it, and show the user a generic failure rather than a field-level message
    about a payload they never saw.
  </Accordion>
</Accordions>

## Form errors

<include meta='title="components/create-user-form.ts"'>../../../../../../examples/src/zod-form-errors.ts</include>

`flatten()` comes from Zod and produces exactly the shape a form wants.
`format()` gives the nested variant, for forms with nested objects.

Note the `target === "body"` guard: without it, a *response* that breaks its
contract would paint field errors on a form the user never filled in wrong.
