`ZodApiClient` wraps an `ApiClient` and adds verbs that take a schema. The return
type is inferred from that schema, so there is no generic to pass and nothing to
keep in sync.

## Creating one

```typescript
import { createZodClient, withZod } from "@api-zero/zod";
import { createClient } from "@api-zero/core";

// From configuration
const api = createZodClient({ baseURL: "https://api.example.com" });

// Or wrap a client you already have
const wrapped = withZod(createClient({ baseURL: "https://api.example.com" }));
```

## Writing

<include meta='title="users.ts"'>../../../../../../examples/src/zod-validated-body.ts</include>

`post`, `put` and `patch` accept either a bare response schema or an object with
`response` and `body`. When `body` is present the payload is validated **before
the request leaves the process** — an invalid body never reaches the network, and
the failure arrives as a `ZodValidationError` with `target: "body"`.

## Configuration goes through `.client`

<Callout type="info">
  `ZodApiClient` deliberately does not mirror the configuration API. Use the
  underlying client — it is the same instance, so configuring one configures
  both.

```typescript
api.client.setAuthToken("a-jwt-token");
api.client.interceptors.request.use(/* … */);
```
</Callout>

Every mirrored method would be one more thing to keep in step with core, falling
silently behind the moment core grows one. Exposing the real client has no such
failure mode.

## Verbs

| Method | Signature |
| ------ | --------- |
| `get` | `(endpoint, schema, options?)` |
| `delete` | `(endpoint, schema, options?)` |
| `post` | `(endpoint, body, schemas, options?)` |
| `put` | `(endpoint, body, schemas, options?)` |
| `patch` | `(endpoint, body, schemas, options?)` |

`options` is the same `RequestOptions` as core: `params`, `signal`, `timeout`,
`retry` and the rest all work unchanged.
