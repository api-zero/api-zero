The adapters turn a schema into plain `RequestOptions`. Use them when you want
schema validation on a client you already have, without wrapping it.

<include meta='title="users.ts"'>../../../../../../examples/src/zod-adapters.ts</include>

Because they return ordinary options, they spread alongside everything else:
`timeout`, `signal`, `params`, `retry`. Nothing is special-cased.

## `zodResponse(schema)`

Returns `{ transformResponse }`. The response is parsed with `safeParseAsync`,
so async refinements and transforms work. On failure it throws a
`ZodValidationError` with `target: "response"`.

Since it is a response transform, it runs **after** the body is parsed and
**before** validation and the response interceptors — so an interceptor sees the
already-validated, already-transformed data.

## `zodBody(schema)`

Returns `{ transformRequest }`. The body is validated before the request is
built, so an invalid payload never reaches the network and fails with
`target: "body"`.

## `zodContract({ response, body })`

Combines both into one options object. `ZodApiClient` is built on it.

<Callout type="info">
  There is no `params` schema. The request pipeline has no params-validation
  hook, and accepting a schema that types query parameters as validated while
  validating nothing is worse than not offering it —
  [ADR-003](https://github.com/api-zero/api-zero/blob/main/docs/adr/003-scope-boundary-and-public-surface.md).
</Callout>

## Adapters or `ZodApiClient`?

| | Adapters | [`ZodApiClient`](/docs/zod/api-reference/zod-api-client) |
| --- | --- | --- |
| Client | Your existing `ApiClient` | A wrapper around one |
| Return type | Pass the generic yourself | Inferred from the schema |
| Composition | Spread into any options object | Schema is an argument |

Inference is the reason `ZodApiClient` exists: `api.get("/users/1", schema)`
needs no generic, and it cannot drift from the schema. Reach for the adapters
when you want validation on a specific call without changing how the rest of
your code gets its client.
