Extends [`ApiError`](/docs/core/api-reference/api-error), so everything that
already handles errors handles this one — the same catch blocks, the same
interceptors, the same `instanceof ApiError` checks.

### Which side failed

`target` is the field to branch on, and the two values call for opposite
responses.

<Accordions>
  <Accordion title='"body" — your bug, recoverable in the UI'>
    The request was malformed before it was sent, so nothing reached the server.
    Surface the issues to whoever built the payload: a form, a caller, a script.
  </Accordion>
  <Accordion title='"response" — their change, or your schema'>
    The server sent something the contract does not describe. Not recoverable in
    the UI — report it, and show the user a generic failure rather than a
    field-level message about a payload they never saw.
  </Accordion>
</Accordions>

## What it inherits

Everything on [`ApiError`](/docs/core/api-reference/api-error): `request`,
`cause`, `attempt`, `status`, `toJSON()` and the `is*()` helpers.

Two are worth knowing about here:

| Inherited | Value for a validation error |
| --------- | ---------------------------- |
| `isValidationError` | Always `true`. |
| `status` | The HTTP status that carried the bad payload, or `0` when the body failed and no request was made. |

<Callout type="info">
  `isRetryable()` returns `false`. A payload that failed the schema fails
  identically on the next attempt, so the retry policy skips it rather than
  spending three attempts to reach the same error.
</Callout>
