`api.get<User>("/users/1")` is a promise you make to yourself. Nothing checks it.
If the API renames a field, drops one, or returns `null` where you expected a
string, TypeScript stays quiet and your code fails somewhere else entirely —
usually in a component, usually with a message that says nothing about the API.

`@api-zero/zod` closes that gap. The schema validates the payload **and**
produces the type, so the two cannot disagree.

## Installation

```bash
pnpm add @api-zero/core @api-zero/zod zod
```

Both `@api-zero/core` and `zod` are peer dependencies: you keep control of the
versions, and there is only ever one copy of each in your tree.

## The shape of it

<include meta='title="lib/api.ts"'>../../../../../examples/src/zod-typed-response.ts</include>

Two things happen at once. `createdAt` arrives as a string and is handed to you
as a `Date`, because the schema said so. And `user` is typed from that same
schema — no interface to keep in sync, no cast.

## When a payload does not match

<include meta='title="users.ts"'>../../../../../examples/src/zod-error.ts</include>

`ZodValidationError` extends `ApiError`, so it flows through the same catch
blocks, the same interceptors and the same `instanceof ApiError` checks as every
other failure. It adds `issues`, the original `zodError`, and `target` — which
tells you whether the request body or the response was at fault.

`flatten()` and `format()` come from Zod and are useful for turning issues into
form errors.

<Callout type="info">
  Validation failures are never retried. A payload that failed the schema will
  fail identically on the next attempt — retrying only delays the error.
</Callout>
